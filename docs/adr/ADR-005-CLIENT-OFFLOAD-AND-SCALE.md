# ADR-005：客户端减载与实时媒体规模分层

- 状态：accepted
- 日期：2026-08-19
- 关联任务：RTC-007、RTC-010；后续拆分为 RTC-011～RTC-015

## 背景

当前项目已经使用 LiveKit SFU 承载 1 对 1、群聊和互动连麦，Spring Boot、Kafka
和聊天 WebSocket 只负责控制面。随着多个独立通话和多人通话同时发生，压力主要集中在
LiveKit 的出站带宽、RTP 包处理、房间/轨道数量和 coturn relay，而不是业务 API 转发媒体帧。

把所有用户改成互相转发媒体不能解决大规模问题：同一房间的 mesh 连接数和客户端上行近似
按参与人数平方增长，移动端、企业网、NAT、后台挂起、恶意中继和隐私风险都会放大。它只适合
受控的 1 对 1 实验，不能作为群聊或万人互动的默认路径。

## 决策

### 1. 按场景选择拓扑

| 场景 | 正式拓扑 | 客户端减载方式 | 禁止事项 |
|---|---|---|---|
| 1 对 1 | LiveKit SFU；未来可灰度 P2P 直连，失败回退 SFU | 直连成功时减少 SFU 媒体流；浏览器负责采集、编码、解码 | 不复用旧 `Call.vue` mesh；不在已接通房间静默换拓扑 |
| 3～8 人群聊 | LiveKit SFU | simulcast、dynacast、可见 tile/主讲人订阅、音频优先 | 不把用户当 relay；不全员强制高层视频 |
| 互动连麦 | LiveKit stage，首期 8 人，后续 16 人需压测 | 只有发布者和必要订阅者进互动房间 | 普通观众加入同一个双向房间 |
| 大规模直播 | SRS ingest + WHEP/LL-HLS/HLS/HTTP-FLV + CDN | 观众主要走 CDN，浏览器只解码自己选的档位 | 让万人进入 LiveKit 房间互发视频 |
| 多个独立房间 | LiveKit 多节点/多地域按房间放置 | 房间级 admission、节点扩容、TURN 区域池 | 单节点承载所有房间而无容量门禁 |

### 2. 客户端可以承担什么

- 摄像头/麦克风采集、回声消除、降噪、编码、解码和渲染本来就由浏览器承担。
- simulcast 让客户端编码低/中/高层，SFU 只转发被订阅的层；dynacast 会暂停没有订阅者的层。
- 选择性订阅、视频质量层切换、隐藏 tile 暂停视频，可以减少 SFU 出站和本端解码压力。
- 1 对 1 P2P 成功时媒体直接在两个用户之间传输；但 TURN 中继时媒体仍会经过服务器，且控制面、授权、审计和失败回退仍然保留。

### 3. 客户端不能承担什么

- 不能把群聊参与者变成公共转发节点来实现“万人通话”。这会把服务器带宽问题换成终端上行、电量、掉线和安全问题。
- 不能让客户端绕过房间 ACL、短期 token、TURN 凭据或控制面状态机。
- 不能把 RTP、音视频帧或原始高频 stats 写进 Spring、Kafka 或聊天 WebSocket。

## 规模模型

设一个房间有 `P` 个发布者，每个视频流平均码率为 `B`：

- SFU ingress 约为 `P × B`。
- 全量订阅的 SFU video egress 约为 `P × (P - 1) × B`。
- 只有 `S` 个主讲/可见视频被订阅时，egress 约为 `P × S × B`，音频另计。
- 多个互相独立的房间按房间求和；它们不会因为在同一产品中就自动共享媒体流。

这些公式只用于容量预算，最终必须用同编码器、浏览器和网络条件的压测数据替换。

## 实施顺序

1. 先采集 LiveKit/SFU、coturn 和客户端 QoE 基线，建立 room admission 和 30% 容量余量门禁。
2. 修复 `RtcMediaPort` 的轨道绑定、可见性和 publication 生命周期契约；随后开启可回滚的 simulcast、dynacast、选择性订阅和 `adaptiveStream`。
3. 将 LiveKit 改为 Redis 共享路由和多节点/多地域房间放置，扩大 TURN 区域池和 relay 端口范围。
4. 直播和万人观看采用 stage + audience：少量主播/嘉宾进入 LiveKit，普通观众使用 SRS/CDN；需要发言的观众申请上麦或进入 breakout room。
5. 最后才评估 1 对 1 P2P fallback，必须有显式 feature flag、双方同意、ICE/质量/隐私指标和 SFU 回退。

## 回滚与验收

- 所有减载策略均由配置或 feature flag 控制，发现首帧、黑屏、冻结或音频异常时可以退回全订阅 SFU。
- 群聊验收至少覆盖 2/4/8 人、全视频、只音频、隐藏 tile、后台 tab、摄像头开关和弱网重连。
- P2P 只比较直连成功率、TURN 比例、SFU egress、RTT、丢包、CPU/电量和通话失败率，不能只看服务器带宽下降。
- “万人”验收必须是 stage + audience 的分层负载，不得用一个万人双向 LiveKit 房间宣称通过。
